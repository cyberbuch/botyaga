# PLAN — миграция на ytbuch към Elixir/Phoenix/Ecto/PostgreSQL

Към 2026-11-15. Изходно приложение: `../ytbuch` (Rust/Axum 0.8, YottaDB r2.06
през Octo 1.1.0, Next.js 16). Цел: `botyaga` — същото приложение, същият API
контракт, същият фронтенд, нова база и нов backend.

## 1. Мотив — честен одит

Заявеният мотив: „по-лесно се ъпдейтва на VPS, не иска дълга компилация“.

**Това е слаб аргумент за миграция.** Elixir също се компилира (`mix release`
за приложение от този мащаб също отнема минути). Решението на проблема с
ъпдейта е **билд в CI + готов артефакт на VPS** — и то работи еднакво добре
за сегашния Rust бинар (единичен статичен файл, дори по-лесен за деплой).
Ако мотивът беше само деплоят, миграцията не си струва риска.

**Силният аргумент е базата.** Octo на този контейнер няма:

- транзакционни записи (`INSERT`/`UPDATE` в транзакция гърмят) — постът на
  фактура е поредица от заявки и прекъсване оставя частичен запис;
- индекси, външни ключове, `SERIAL`, `ALTER TABLE`, `TIMESTAMPTZ`;
- разширен Postgres протокол — всичко е simple query с ръчно екраниране.

Целият код е деформиран около тези липси: `*_extra` таблици вместо колони,
`MAX(id)+1` вместо identity, ръчно триене на частични записи, никакъв
интегритет освен приложението. PostgreSQL + Ecto премахва тези деформации и
прави атомния пост възможен. Това е реалната печалба; деплоят е страничен
ефект, който се решава с CI независимо от езика.

Изводът: миграцията се прави заради интегритета на счетоводните данни и
поддръжката, не заради „без компилация“. Компилация остава — просто не на VPS.

## 2. Решения

| # | Решение | Избор | Алтернативи (отхвърлени) |
|---|---------|-------|--------------------------|
| 1 | Обхват | Същото приложение: `/v1` контрактът и Next.js фронтендът се запазват 1:1 | LiveView пренаписване на UI — двоен обхват, нов риск, няма полза за потребителя |
| 2 | Phoenix режим | JSON API без LiveView, без asset pipeline на Phoenix | `--live` — излишен, фронтендът е Next.js |
| 3 | Frontend | Копие на `ytbuch/frontend` без промени (само `YTBUCH_API_PROXY` сочи новия порт) | Пренаписване — виж т. 1 |
| 4 | Пари в базата | `numeric` (пари 2 знака, количество 4, вътрешен мащаб 6 за склада); в JSON остават низове | VARCHAR като в Octo — губи се смисълът на Postgres; float — никога за пари |
| 5 | Идентификатори | `bigserial`/identity; при импорт на данни старите `id` се запазват | `MAX(id)+1` — race condition, в Postgres е безсмислено |
| 6 | Схема | `*_extra` таблиците се сливат в основните (`user_login`→`users`, `counterpart_extra`→`counterparts`, `invoice_extra`→`invoices`, `invoice_line_extra`→`invoice_lines`). API формата не се променя | Запазване на extra таблиците — вече няма причина за тях |
| 7 | Интегритет | FK + индекси + уникални ограничения (ЕИК, номер сметка във фирма, IBAN във фирма); `company_id` навсякъде | Само приложението пази връзките — както досега, но вече без оправдание |
| 8 | Транзакции | `Ecto.Multi` за пост/отпост/триене на фактура, складово преизчисление, производствена поръчка, амортизация. Компенсаторното триене на частични записи отпада | Ръчна компенсация като в Rust — вече не е нужна |
| 9 | Автентикация | Същият JWT HS256 (7 дни, `ver` сесийна версия, `mfa` claim), argon2id през `argon2_elixir`, наследените sha256 хешове се мигрират при вход както досега | Нова auth схема — чупи фронтенда и сесиите |
| 10 | Печат | PDF: HTML шаблон → headless Chromium (страничен контейнер `print`). DOCX/ODT: нативен Elixir (`:zip` + XML шаблони, DejaVu шрифтът в release-а) | Rust print sidecar — връща Rust в стека; чист Elixir PDF (pdfbox-подобен) — незрял за кирилица и таблици |
| 11 | Външни услуги | Finch/Req (ЕЦБ, VIES, Mistral), Swoosh (SMTP), ExAws (S3, path-style) | — |
| 12 | Windows-1251 | `codepagex` за ДДС файловете; ZIP без компресия през `:zip` | — |
| 13 | Rate limit | Per-user кош зад JWT (300 накуп / 20 на сек), по-строг IP кош за вход/регистрация (30 / 2 на сек) — както в `rate_limit.rs` | IP-only — зад проксито всички са един адрес |
| 14 | Деплой | CI билдва `mix release` tarball + Next.js build; VPS получава артефакти и рестартира. Erlang runtime е в release-а, Node само за Next контейнера | Компилация на VPS — точно това избягваме |
| 15 | Име/портове | `botyaga`, API 8093, UI 3021, PG 5433 — успоредно с ytbuch до cutover | Същите портове — не могат да вървят едновременно за сравнение |

Версиите (Elixir/OTP/Phoenix/Ecto) се сверяват с актуалната документация при
генерирането на скелета — не се фиксира по памет.

## 4. Данни и Ecto схема

Принципи:

- Парите са `:decimal` в Ecto, `numeric` в PG. JSON view-то ги форматира
  като низове (2/4 знака) — контрактът не се променя.
- Дати/часове: истински `date`/`utc_datetime` вместо VARCHAR. Външният формат
  в JSON остава както досега (`YYYY-MM-DD`, unix секунди където ги има).
- `settings` остава key/value (включително `активна_фирма:<sub>`,
  `auth.jwt_secret`, SMTP/S3 с маскиране `••••••••`). Тайните не се връщат
  през API-то и не влизат в repo-то.
- Уникални индекси: `users.email`, `companies.eik`,
  `accounts(company_id, number)`, `counterparts(company_id, eik/vat)`,
  `bank_accounts(company_id, iban)`, `document_series` типове във фирма.
- FK с `on_delete` поведение, което повтаря сегашното ръчно триене
  (напр. фактура → редове → дневник; контрагент → extra адрес вече е слят).
- Всяка заявка по `id` проверява `company_id` на активната фирма — чужд ред
  е 404, както досега. Това остава в заявките (не се разчита само на FK).
- Миграциите са нормални Ecto миграции с版本号 — край на `CREATE TABLE IF
  NOT EXISTS` при всеки старт и маркерите в `schema_migrations`.

## 5. Деплой — решението на проблема с VPS

```
CI (GitLab/GitHub)                     VPS
─────────────────────                  ─────────────────────────
mix deps.get && mix release   ──►      botyaga.tar.gz (вкл. ERTS)
npm ci && npm run build       ──►      next build артефакт
docker build (PG, print)      ──►      образи / tarball
                                       │
                                       ▼
                            разархивирай + systemctl restart botyaga
                            (или docker compose pull && up -d)
                            миграции: botyaga eval "Release.migrate"
```

- На VPS няма Elixir, Erlang-devel, Rust, Node-devel — само runtime.
- Ъпдейт = качи артефакт + рестарт (секунди). Компилацията остава в CI.
- PostgreSQL: контейнер с volume, `pg_dump` по cron + S3 бекъп през
  съществуващия механизъм (`ytbuch_backup_*.sql.gz` форматът се запазва).
- Release-ът носи DejaVu шрифта и каталозите — никакви системни зависимости.
- Тайни (`JWT_SECRET`, DB парола, SMTP, S3, Mistral) са само в env на VPS.
  Празна база → еднократна superadmin парола в лога, както в ytbuch.

## 6. Фази

Всяка фаза завършва със зелени тестове и сравнение срещу работещия ytbuch
(контрактни тестове: еднакви заявки → еднакви JSON отговори).

### Фаза 0 — скелет и CI (1–2 дни)
`mix phx.new botyaga --no-html --no-assets --no-live --ecto`, PostgreSQL,
release конфигурация, CI pipeline (билд + тестове + артефакти), Docker
compose за локална разработка (PG + print). Gate 400/600 в CI.
**Готово когато:** празен release се деплойва на тестов VPS с една команда.

### Фаза 1 — основа: вход, фирми, права (седмица 1–2)
`Accounts`, `Access`, `Companies`: JWT + argon2id + sha256 наследство,
2FA/TOTP, сесийна версия, gate plug pipeline, роли и членства, активна
фирма, табло, настройки на фирма (обекти, собственици, майки, серии),
глобални настройки с маскиране, rate limit. Seed на ролите и superadmin.
**Готово когато:** съществуващият Next.js login/профил/фирми екрани работят
срещу новия API без промяна; `POST /v1/auth/token` връща същия формат.

### Фаза 2 — номенклатури (седмица 2–3)
`Catalog`: сметкоплан + seed от НАП (360 сметки, без дублиране), контрагенти
(ЕИК/ДДС дубликат проверка, `999999999` еднократни), стоки (вид запас, КН8,
авто-код), 12-те номенклатури, `/v1/units`.
**Готово когато:** seed-ът дава 361 сметки за демо фирмата както в ytbuch;
списъчните екрани странират по 50 с търсене.

### Фаза 3 — ядро: фактури, дневник, периоди (седмица 3–5)
`Invoicing`, `Journal`, `Periods`: чернови, серии и следващ номер, суми
(стотинки/мащаб 6), пост/отпост/триене в **една транзакция**, черно сторно,
проформа, bulk операции, универсална статия (количество × курс, валутни
сметки 4xx/5xx), затворен месец спира поста, начални салда, приключвателни
операции (`closing_map`, най-дълъг префикс).
**Готово когато:** демо фирмата възпроизвежда двата ѝ записа в дневника
бит по бит; прекъснат пост не оставя частичен запис (тест със симулирана
грешка); сборът дебит=кредит важи на ниво база (constraint/trigger).

### Фаза 4 — ДДС (седмица 5–6)
`Vat`: дневници от записите + редовете на фактурите, ръчни клетки,
DEKLAR/POKUPKI/PRODAGBI/VIES в Windows-1251, ZIP без компресия, VATEX.
**Готово когато:** файловете минават позиционната проверка спрямо примерните
подавания на НАП (референците остават в `ytbuch/secret`, не се копират тук).

### Фаза 5 — банки, ДМА (седмица 6–7)
`Banking`: CSV, MT940, XML (Postbank, UniCredit, OBB, camt.053), правила с
ключови думи и приоритет, шаблони, авто-разнасяне, осчетоводяване.
`Assets`: категории, амортизация (Дт 603/Кт 241), събития.
**Готово когато:** импорт на референтно извлечение дава същите редове като
ytbuch; амортизационният запис съвпада.

### Фаза 6 — склад, производство, дивиденти (седмица 7–9)
`Stock`: WAC/FIFO/LIFO, преизчисление от началното салдо по документи
(редът за един ден се пази), партиди, правила, месечно изписване на
себестойност, ръчни материали МИ-{id}, протоколи, справка.
`Production`: рецепти, поръчки ПР-{id}, потвърждение с междинна сметка.
`Dividends`: разпределения, 5% данък, плащане.
**Готово когато:** преизчисление на идентични документи дава идентични
наличности и себестойност като ytbuch (property тестове върху WAC/FIFO/LIFO).

### Фаза 7 — справки и финансови отчети (седмица 9–10)
`Reports`: оборотна, главна книга, кореспонденции, хронология, контрагентни,
баланс/ОПР/паричен поток/капитал от `fs_line_formulas`, формули с валидация,
PDF/XLSX/ODS експорт, `bg=1` формат на числата.
**Готово когато:** всички `kind`-ове връщат същите суми като ytbuch върху
демо данните и върху импортирана реална фирма.

### Фаза 8 — SAF-T (седмица 10–11)
`Saft`: monthly/annual/ondemand XML по BG_SAFT_Schema V1.0.1, заглавка
(област, МОЛ, Ownership), данъчни кодове, съпоставяне на движения.
**Готово когато:** XSD валидация минава за същите периоди, за които минава
ytbuch; известените ограничения (месец без плащане и т.н.) се държат едно към
едно — не се „подобряват“ скрито.

### Фаза 9 — печат, UBL, външни услуги (седмица 11–12)
`Printing`: PDF през Chromium sidecar, DOCX/ODT нативно, сума словом,
UBL 2.1 (CreditNote 381, проформа 325, TaxCurrencyCode).
`Integrations`: ЕЦБ (daily + 90d hist, as-of), VIES SOAP, Mistral OCR +
адреси, UBL вход → чернова, product_name_mappings.
**Готово когато:** отпечатаната фактура е визуално идентична (сравнение на
рендер), UBL минава валидатор, OCR връща същата чернова за референтен скан.

### Фаза 10 — админ, архив, одит (седмица 12–13)
SMTP тест, S3 тест/бекъп/списък/триене, db-check, одитна следа с потребител
и timestamp, демо фирма YT ООД при първи старт.
**Готово когато:** `pg_dump` бекъпът се възстановява в чиста база и
приложението тръгва; одитът пази същите полета.

### Фаза 11 — миграция на данни и cutover (седмица 13–14)
1. Логически SQL dump от ytbuch (`ytbuch_backup_*.sql.gz`, вече съществува).
2. Зареждане в staging схема в PG (таблиците са VARCHAR-съвместими).
3. Трансформация към новата схема: сливане на `*_extra`, VARCHAR → numeric/
   date, запазване на `id`, пресмятане на sequence-ите след импорта.
4. Верификация: брой редове по таблица и фирма; оборотна ведомост и ДДС
   дневници за всички периоди съвпадат с ytbuch до стотинка; сбор дебит=кредит.
5. Успореден период: двата стека работят, новите данни се въвеждат само в
   единия (замразяване на ytbuch преди финалния импорт).
6. Cutover: финален dump → импорт → превключване на проксито/порта →
   ytbuch остава read-only за справка.

**Готово когато:** реална фирма минава през всички справки еднакво в двата
стека и потребителите работят само в botyaga.

## 7. Тестова стратегия

- **Контрактни тестове:** таблица заявка → очакван JSON, пускана срещу двата
  API-та (golden master от ytbuch). Пази формата `items`/`count`, `detail`,
  низовете суми, статус кодовете (409/422/404/403) и българските съобщения.
- **Счетоводни тестове:** дебит=кредит след всяка операция; черно сторно;
  затворен месец; WAC/FIFO/LIFO property тестове; атомност на поста.
- **Файлови тестове:** XSD за SAF-T, позиционна проверка за НАП файловете,
  UBL валидатор.
- **Печат:** snapshot сравнение на рендер спрямо ytbuch.
- Всички батерии зелени преди всеки push (CI gate).
