# Доклад: Продукция ръчен приход

Дата: 2026-11-25 · Модул: `production_receipts` · UI: `/production-receipts` (право `production`)

## 1. Защо е нужен модулът

Стандартното производство в системата работи по **рецепти и производствени
поръчки** (`production_orders` + `recipes`), а себестойността се сглобява
автоматично в `Stock.Replay`. При **производство по поръчка** всяко изделие е
различно и не може да се автоматизира по този начин — затова натрупаните
разходи стоят в сметките, а приходът на готова продукция се прави ръчно за
месец.

Счетоводната рамка:

| Операция | Запис |
|----------|-------|
| Продажба на продукция | КТ **701** Приходи от продажба на продукция |
| Готова продукция | сметка **303** |
| Приход на продукция | **ДТ 303 / КТ 611** Разходи за основната дейност |
| Непреки разходи | натрупват се в **612** (61201 преки, 61202 непреки) |
| Изписване на продаденото | **ДТ 701 / КТ 303** — в 303 вече е пълната стойност |

Сметките не са твърдо забити: вземат се от настройките на артикула —
303 = `inventory_account_id`, 701 = `revenue_account_id`, 611 =
`expense_account_id` (при липса — клиринговата сметка от правилото
`kind = "production"` за двойката инвентарна/приходна).

## 2. Работен поток (трите таба)

### Таб 1 — Произведено
`GET /v1/production-receipts/preview?month=YYYY-MM` връща:

- продаденото по **КТ 701** за месеца — от posted фактури за продажба
  (`direction = "out"`, тип 01/11), agrupирано по артикул: количество и приход;
- **натрупаната стойност в 611** за месеца (нетен дебитен оборот по префикс
  `611` от дневника, параметър `expense_prefix`);
- натрупаните **непреки разходи по 612** (префикс `612` без `61201`,
  параметри `indirect_prefix` / `indirect_exclude`).

Потребителят задава в празното поле **„Наличност в края“** на ред:

```
произведено = продадено + наличност
единична цена = натрупаното в 611 / общо произведено
стойност на реда = произведено × единична цена     (Σ по редовете = 611)
```

UI-ът преизчислява **на живо** единичната цена и стойността на продаденото при
въвеждане на наличността (същата формула като при запис), така че числата в
прегледа съвпадат с тези, които ще се потвърдят.

### Таб 2 — Разпределение 612
Натрупаните непреки разходи (612 без 61201) се разпределят **пропорционално на
произведената стойност по артикул**, със закръгляне до стотинки; последният
ред поема остатъка, така че сумата винаги е точна. Резултатът се пази в
`production_receipt_allocations` (сметка, артикул, база, сума).

### Таб 3 — Записи
При потвърждаване се пише **един балансиран journal запис**
(`document_type = "production_receipt"`, дата = последният ден на месеца):

| Ред | Дебит | Кредит | Сума |
|-----|-------|--------|------|
| приход на продукция | 303 | 611 | произведена стойност по артикул |
| разпределение 612 | 303 | 61202… | разпределена сума по сметка |
| продадено | 701 | 303 | продадено × пълна единична цена (с разпределението) |

След записа в **303 остава точно наличността** на пълна себестойност
(преки + непреки), а 701 остава нетно с маржа.

## 3. API

| Метод | Път | Описание |
|-------|-----|----------|
| GET | `/v1/production-receipts/preview?month=YYYY-MM` | таб 1 + 611/612 за месеца |
| GET | `/v1/production-receipts` | списък документи |
| POST | `/v1/production-receipts` | `{month, notes, lines: [{product_id, ending_quantity}]}` → чернова ПР-{id} |
| GET | `/v1/production-receipts/:id` | документ с редове, разпределения, audit |
| PATCH | `/v1/production-receipts/:id` | чернова: бележка + наличности по ред |
| DELETE | `/v1/production-receipts/:id` | само чернова |
| POST | `/v1/production-receipts/:id/confirm` | преизчислява, пише journal запис, статус confirmed |
| POST | `/v1/production-receipts/:id/unpost` | изтрива записа, връща в чернова |

## 4. Контроли и инварианти

- **един потвърден документ на месец** — втори дава 409;
- периодът на документа трябва да е **отворен** (`Periods.assert_open`);
- при потвърждаване стойностите се **преизчисляват от текущия оборот на 611**
  (ако между създаване и потвърждаване са влезли още разходи, записът ги взема);
- без натрупана стойност в 611 → 422 „записът на разходи липсва“;
- записът е винаги балансиран (дебит = кредит); при празни страни запис не се
  създава (`journal_entry_id = 0`);
- пълен audit trail (`production_receipt`: create/update/delete/post/unpost);
- gate: сегментът `production-receipts` изисква право `production`
  (и `audit-logs/production_receipt` → `production`).

## 5. Модел на данните

Миграция `20261125112408_create_production_receipts.exs`:

- `production_receipts` — фирма, номер ПР-{id}, дата, месец, статус, бележка, `journal_entry_id`;
- `production_receipt_lines` — ред: артикул, продадено (бр./сума), наличност,
  произведено (бр.), единична цена, сума, разпределено, за изписване,
  трите сметки от артикула;
- `production_receipt_allocations` — разпределение по (сметка 612, артикул).

## 8. Известно ограничение

Модулът е **journal-ориентиран** и не пише в партидите на `Stock.Replay`
(наличностите по обекти в складовата справка не включват ръчния приход) —
умишлено, защото производството по поръчка е извън автоматичното преизчисление.
Ако складовата справка трябва да вижда и 303 от ръчни приходи, следващата
стъпка е приходът да се добави като `:in` движение в `Stock.Replay.Load`.
